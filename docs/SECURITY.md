# Безопасность Элиана: модель угроз

## 0. Главное, что нужно принять

**В Элиане нет E2E-шифрования.** Сервер (то есть владелец телефона) технически может прочитать сообщения:
они расшифровываются в памяти процесса. Шифрование здесь — «at rest»: база (SQLCipher) и медиа (AES-256-GCM)
защищены ключами, без которых файлы бесполезны. Никогда не называйте это сквозным шифрованием.

## 1. Активы

| Актив | Где | Защита |
|---|---|---|
| Пароли | `credentials.password_hash` | Argon2id (19 MiB, t=2, p=1), уникальная соль |
| Сессии | `sessions` | хранится только SHA-256 токена + pepper; cookie `HttpOnly`, `SameSite=Lax`, `Secure` в проде |
| CSRF | cookie + серверная привязка к сессии | double-submit, проверка на все мутирующие методы |
| Коды подтверждения | только консоль/Termux-уведомление | не хранятся в открытом виде (хэш), TTL 5 мин, одноразовые |
| Медиа | `~/.elian/data/media` | AES-256-GCM, чанки по 64 КиБ, ключ `MEDIA_KEY` (600, вне данных) |
| База | `~/.elian/data/elian.db` | SQLCipher, ключ `DB_KEY` (600, вне данных) |
| Бэкапы | `~/.elian/backups/*.elnb` | отдельная парольная фраза, независимая от ключей БД |

## 2. Кто против нас и что мы делаем

### 2.1 Украденный/потерянный телефон
- Диск: база и медиа бесполезны без `secrets/` — но если телефон разблокирован, приложение Termux имеет доступ к ключам.
  Реальный контроль: блокировка экрана Android, шифрование устройства, отдельный профиль.
- **Уведомления на экране блокировки** показывают логин и (по умолчанию) код подтверждения.
  Это удобно и это утечка. Отключить: `OWNER_NOTIFICATION_SHOW_CODE=false`.
- Рекомендация: храните `backup-passphrase.key` вне телефона.

### 2.2 Владелец сервера (вы) как потенциальный «злоумышленник»
- Вы видите метаданные и текст сообщений, но **не** пароли, не хэши, не токены, не cookie, не approval-секреты
  в консоли/уведомлениях/логах (централизованный редактор + отсутствие таких данных в выводе).
- Аудит-лог фиксирует действия (вход, смена пароля, бан, экспорт), но не содержимое сообщений.

### 2.3 Пользователь, который хочет перебрать пароли
- Argon2id + общая задержка на неудачный вход; rate limit по IP и по логину.
- Одинаковый ответ «Неверный логин или пароль» и одинаковое время для существующего и несуществующего пользователя
  (фиктивная проверка хэша).
- Заявка на вход создаётся **только** после успешной проверки пароля: на провал — ни заявки, ни кода, ни лога с логином.

### 2.4 Спам и перегрузка
- Rate limit на регистрацию, логин, сброс, поиск, загрузку медиа, создание чатов, реакции, заявки.
- Медиа ограничены `MEDIA_MAX_BYTES` (по умолчанию 100 МБ), лимит тела запроса 2 МБ для JSON.
- Slow mode, права участников, баны, ограничения канала (писать может только админ).

### 2.5 Cloudflare / сеть
- TLS терминируется на границе Cloudflare; ниже — туннель до телефона. Cloudflare видит трафик так же, как и вы.
- Сервер доверяет `CF-Connecting-IP` только при `TRUST_CLOUDFLARE_PROXY=true`; обычный `X-Forwarded-For` игнорируется.
- Сервер слушает `127.0.0.1`; `0.0.0.0` — только осознанный LAN-режим.

### 2.6 Клиент (веб/PWA)
- Никакого `localStorage` с токенами: сессия в HttpOnly-cookie.
- XSS-поверхность: React-экранирование, свой набор иконок, Markdown-подобное форматирование парсится на сервере
  и отдаётся как entities (никакого `dangerouslySetInnerHTML`).
- Dexie/IndexedDB хранит кэш сообщений на устройстве (для офлайн-режима) — это ожидаемый компромисс;
  при выходе кэш можно очистить в настройках («Данные и память»).

## 3. Что гарантируется проверками

Покрыто автотестами (см. `docs/TEST-REPORT.md`):
- пароль-маркер не встречается в логах, ответах API, бэкапах и уведомлениях;
- клиент никогда не получает код подтверждения;
- без `y` владельца сессия не создаётся; перезапуск сервера не «подтверждает» заявку;
- повторное использование заявки/тикета отклоняется;
- публичный HTTP-вызов подтверждения невозможен (маршрута нет);
- чужая сессия, не-участник чата, чужое медиа и чужие настройки недоступны;
- отсутствие CSRF-заголовка → 403; чужой Origin → 403;
- `privacy.lastSeen='nobody'` скрывает присутствие; блокировка запрещает отправку;
- подписчик канала не может писать; токен инвайта хранится только хэшем.

## 4. Осознанные ограничения

- Нет E2E, нет секретных чатов, нет самоуничтожающихся сообщений.
- Один сервер = один телефон: компромисс устройства компрометирует всё.
- Групповые звонки требуют внешнего SFU; TURN для 1:1 нужно поднимать отдельно.
- Парольная фраза бэкапа может лежать рядом с архивом (по умолчанию) — защита от кражи телефона требует
  ручного переноса фразы.

## 5. Сообщить об уязвимости

Опишите шаги воспроизведения владельцу сервера приватно; не публикуйте PoC до исправления.
